# 用 Nexent Skill 继续优化验收指标：诊断、技能设计、落地顺序

> 现状：检出 96.0% / 误报 6.5% / 定位 100% / 等级 100% / 建议可用 94.4% / 一致性 1.000，六项全部达标。
> 本文回答一个问题：在这个位置上，Skill 应该怎么用才真的能提指标，而不是把提示词换个地方放。

---

## 0. 结论先行

1. **残余误差只剩两簇，且都可机械化**：5 条误报里 4 条是 R16（最高额担保），3 条漏检全部是 R38（电子签名效力）。这不是"模型不够聪明"，是"本就该由代码做的判断交给了模型"。
2. **先用确定性闸门清零这两簇，再谈 Skill**。本仓库已附原型 `tools/gate.py`，在不改模型的前提下把指标推到 100% / 2.6%（见 §1.3）。
3. **Skill 的真实价值是上下文分层，不是新增推理能力**：把 40 条规则的判定知识从"常驻提示词 + 语义检索"改成"按需加载的规则卡"，同时给演示增加"技能调用"这一层可展示的编排。
4. **决定权必须留在代码里**：Skill 是否激活由模型判断，天然不确定；`3 次一致性 1.000` 是最脆的指标，不能交给"模型记得调用技能"。
5. **别用这套测试集把指标刷到 100% 就收工**：75 条计分标注，1 条 = 1.3pp；继续在同分布上优化，收益是"拟合"，不是"能力"。留出集才是下一步的重点。

## 一、先把问题看清楚

### 1.1 误差的形态：两簇，不是弥散

| 簇 | 数量 | 表现 | 根因（从 `data/review/fp_list.md` 与预测原文核对） |
|---|---:|---|---|
| R16 误报 | 4（C02/C09/C12/C21） | 条款已写明「最高债权额为人民币 X 万元」，仍被判风险 | 模型**自造判据**："最高债权额应与本金区分""应高于本金"。规则卡的判定条件只有"是否写明具体最高债权额及其构成"，条款已满足。属于"引入规则未列明判据"，现有自证要求拦不住——因为它复述的是规则原文，论证用的却是新判据。 |
| R34 误报 | 1（C02-068） | 管辖条款被判"连接点虚构" | 合同里写的是占位符「示例市」。这是**样本构造瑕疵**，不是模型错误。数据侧修即可。 |
| R38 漏检 | 3（C03/C21/C25） | 条款存在但效力表述不利，未报 | 规则标题是「电子签名/电子合同效力条款**缺失**」，模型只做"有无"判断；条款「电子签名效力以出借人系统记录为准」确实存在，于是被判为"不缺失"。同时提示词「不可判定事项」列了"签约过程/身份核验"不可判，模型顺手把签名类整块放弃了。**规则表述缺陷 + 指令冲突**。 |

一句话：**误报是"多加了规则里没有的判据"，漏检是"规则标题写窄了"。两者都不是语义理解问题。**

### 1.2 为什么继续调提示词收益递减

提示词从 38% 压到 6.5% 靠的是"自证要求"，本质是让模型**自我约束**。剩下的两类错误需要的不是更强的自我约束，而是**外部否决权**：模型说"这条违反 R16"时，需要一个不看语义、只看定式的检查把它按住。这件事 LLM 做不可靠，代码做 100% 可靠。

### 1.3 验证：机械闸门的效果（已在本仓库跑通）

```bash
python tools/gate.py --data-root data
python tools/evaluate.py --data-root data
```

| 指标 | 现状 | 加闸门后 | 说明 |
|---|---:|---:|---|
| 风险条款检出率 | 96.0% | **100.0%** | 补报 3 条 R38 缺陷定式 |
| 误报率 | 6.5% | **1.3%** | 否决 4 条 R16，剩 1 条 R34（数据瑕疵） |
| 定位准确率 | 100% | 100% | 未触碰 |
| 等级一致率 | 100% | 100% | 补报等级取规则表默认值（低），与标注一致 |
| 建议可用性 | 94.4% | 94.7% | 补报 3 条均带完整建议 |

> 上表是 11-06 首轮（旧预测）的结果。接入四个技能后模型输出变化，闸门噪声更多，
> 全量实测为 **100.0% / 2.6%**，详见 `docs/TEST_REPORT.md`。

**这条实验的价值不在数字，而在结论：残余错误里 7/8 条是"定式可判"的。** 定式判定不该出现在提示词里，也不该指望 Skill 正文约束模型——它应该是一段可执行、可回归、可解释的代码。

> 注意：这是在 28 份合成合同、75 条计分标注上的结果，属于"证明可分离"，不是"证明泛化"。闸门规则必须由 `rules.yaml` 生成，且每条规则要显式声明"哪部分可机械判定"，否则就是把测试集写死。

## 二、Skill 能做什么、不能做什么

Nexent 的 Skill = `SKILL.md`（元数据 + 正文）+ 可选 `config/schema.yaml`、`scripts/`、`examples.md`。关键机制是**懒加载**：模型判断需要时才把正文和工具集注入上下文，而不是像工具那样每次思考都占上下文。

| 能力 | 能否靠 Skill 解决 | 说明 |
|---|---|---|
| 40 条规则的判定知识太长，塞不进提示词 | ✅ | 按规则族放 `<reference>`，引用时才加载 |
| 知识库语义检索召回"相近但无关"的规则 → 套错规则 | ✅（可显著缓解） | 规则卡按 rule_id 精确返回，不走向量相似度 |
| 演示"智能体编排 / 技能调用" | ✅ | SSE 里能看到技能激活与脚本执行 |
| 技能可复用、可上架、可版本化 A/B | ✅ | 草稿 v0 / 发布 v1，可申请上架到租户仓库 |
| 字符级定位、正则/数值判定 | ❌ | 必须代码 |
| 保证"每次都会调用这个技能" | ❌ | 激活由模型判断；只能靠提示词强约束 + 代码兜底 |
| 降低单份耗时 | ❌（多数情况相反） | 每次技能调用都增加一轮 tool call |
| 提升 `3 次一致性 Jaccard` | ❌ | 不确定性来源，需回归验证 |

**设计原则：Skill 承载"判定知识"，代码承载"判定执行"。**
技能里写"这条规则怎么判、什么算合规、什么情况必须报"，脚本/服务端写"给定条款文本，机械地否决或补报"。

这也解释了他们已经踩过的坑：把合规范式放进**知识库**会抬高该规则的检索权重、反而增加误报。放进 Skill 后是另一回事——Skill 是**精确注入 + 否决式使用**（由闸门判断，不是由模型"参考"），不会污染其他规则的注意力。

## 三、技能矩阵

四个核心技能 + 一个可选。命名遵守平台规范（全小写、连字符）。

| # | 技能 | 类型 | 何时激活 | 输入 → 输出 | 打哪个指标 | 优先级 |
|---|---|---|---|---|---|---|
| 1 | `loan-rule-cards` | 知识类 | 判定任一 R01–R40 前 | 规则号/条款文本 → 规则卡（判定条件 / 合规定式 / 缺陷定式 / 禁报形态 / 默认等级 / 建议模板） | 误报率（套错规则、自造判据） | P0 |
| 2 | `missing-clause-audit` | 流程类 | 规则表述含"未约定/缺失"，或全文检索不到对应文字 | 条款全文 + 规则号 → {缺失 / 形式具备但效力不足 / 合规} + 锚定条款 | 检出率（R38 型漏检） | P0 |
| 3 | `risk-selfcheck` | 流程类 | 输出 JSON 前 | 候选风险清单 → 保留/删除清单 + 删除原因 | 误报率、一致性 | P1 |
| 4 | `suggestion-compiler` | 流程类 | 生成 `suggestion` 时 | 规则号 + 原条款 + 合同要素 → 可直接替换的完整条款 | 建议可用性 | P1 |
| 5 | `legal-basis-lookup` | 知识类（可选） | 需要 `legal_basis` 时 | 规则号 → 法规原文（只返回命中原文，不生成） | 可信度 / 建议可用性 | P2 |

### 3.1 `loan-rule-cards`：把"规则"变成"判定卡"

这是最该先做的。当前规则知识有两条通路：常驻提示词（只有闸门，没有 40 条细则）和知识库（top_k=3 语义检索）。前者不够用，后者召回不稳——`fp_list` 里 25/28 条误报是"规则套用错误"，正是检索把相近规则递给了模型。

规则卡要固定五段，缺一不可：

1. **判定条件**：逐字来自 `rules.yaml` 的 `llm_hint` + `evidence_spec`，不许改写。
2. **合规定式**：条款长什么样就一定不算违反（例：R16「最高债权额为人民币 X 万元，包括本金……费用」）。
3. **缺陷定式**：条款长什么样一定算违反（例：R16「以出借人核定的授信余额为准」「具体最高额度以……为准」）。
4. **禁报形态**：常见误判及原因（例：金额等于本金 ≠ 违反；未约定复利 ≠ 违反）。**这一条是专治自造判据的。**
5. **默认等级 + 建议模板**：来自规则表，避免模型自由发挥。

用 `<reference>` 按族拆分（利率/担保/违约/合规），SKILL.md 只留索引与使用纪律，单族被引用时才加载该族的 10 张卡。

### 3.2 `missing-clause-audit`：专治"有但不够"

这类风险的判定必须分三态，而不是二态（有/无）：

| 形态 | 判据 | 结论 |
|---|---|---|
| 缺失 | 全文（含附件、表格）用同义词表检索仍无对应约定 | 报，锚定最相关条款 |
| 形式具备、效力不足 | 有约定，但把效力交给一方单方记录、排除法定要件、未约定交付/存证 | **报**（这就是 R38 的 3 条漏检） |
| 合规 | 有约定且满足要件（可靠电子签名、同等效力、可下载文本、时间戳） | 不报 |

关键纪律：**"不可判定事项"指的是签约过程与真实意思表示，不是"条款效力要件"**。这条边界要在技能里写死，否则会和提示词里的"不可判定事项"打架——这正是现在漏检的直接原因。

### 3.3 `risk-selfcheck`：把"自证要求"升级为可核对的清单

现有自证要求让模型复述判定条件，但复述完仍可以偷换论证。自检清单要改成**可判定的四问**，任一为否即删除：

1. 判定条件是否**逐字**出现在规则卡里？（不是"我觉得应该"）
2. `quote` 是否是当前条款正文的**连续子串**？（不是拼接、不是跨条）
3. 条款文本里是否有**直接对应**的文字支撑该判据？（指不出 → 删）
4. `risk_level` 是否等于规则卡默认等级，或有明确的升级依据？

建议输出里带一个 `selfcheck` 字段（`{"rule_card": "R16", "quote_verbatim": true, "criterion_source": "card"}`），既方便服务端二次校验，也让演示时"审查过程"可见。

### 3.4 `suggestion-compiler`：把建议从"一段话"变成"可替换条款"

现在的建议可用性口径是"建议里是否出现该规则的 `suggestion_keywords`"（见 `tools/evaluate.py`），94.4% 意味着 4 条没命中关键词。**这个口径很容易刷**，不建议把 100% 当目标。真正该做的是：

- 结构固定：`主体 + 触发条件 + 数值/口径 + 违约后果 + 救济`；
- 要素回填：合同已有的金额、利率、期限必须继承，不许留 `【】` 占位；
- 与原条款长度可比（±50%），避免"一句话打发"；
- 保留商业条款，只改法律表述。

然后**升级口径**：关键词命中作为底线，另抽 20 条做人工/LLM rubric 评分（完整性、可替换性、要素保留、合规性），两个数一起报。评委会更信后者。

## 四、SKILL.md 骨架（可直接改成上传包）

### 4.1 `loan-rule-cards/SKILL.md`

```markdown
---
name: loan-rule-cards
description: 贷款合同审查的规则卡。当需要判定某条款是否违反 R01–R40 中某条规则时使用：
             输入规则编号或条款文本，返回该规则的判定条件、合规定式、缺陷定式与禁报形态。
             不要在生成修改建议时使用（那用 suggestion-compiler）。
tags: [contract-review, rules, compliance]
---

# 规则卡

## 为什么需要它
知识库是语义检索，会把"措辞相近但判定条件不同"的规则一起召回，
导致把 A 规则的问题挂到 B 规则上——这是本项目历史上最主要的误报来源。

## 使用纪律（必须遵守）
1. 判定只能依据卡里的【判定条件】逐字内容，不得扩展、类推、引入行业惯例。
2. 卡里没有的判据 = 不能用。例如 R16 只判"是否写明具体最高债权额及其构成"，
   **不得**因为"金额等于本金""未区分本金限额"而判违反。
3. 命中【合规定式】→ 直接不报，不再讨论。
4. 命中【缺陷定式】→ 必须报。
5. 返回的默认等级直接用作 risk_level，除非卡里给了升级条件且条款满足。

## 规则族索引
<reference path="cards/interest.md" />    <!-- 利率 R01–R10 -->
<reference path="cards/guarantee.md" />   <!-- 担保 R11–R20 -->
<reference path="cards/breach.md" />      <!-- 违约 R21–R30 -->
<reference path="cards/compliance.md" />  <!-- 合规 R31–R40 -->

## 单卡格式（每族文件内按此写）
### R16 最高额担保未约定最高债权额
- 判定条件：是否写明具体最高债权额及其构成
- 合规定式：本最高额担保所担保的最高债权额为人民币 X 万元，包括本金、利息…
- 缺陷定式：具体最高债权额以出借人核定的授信余额为准 / 保证人在最高额度内提供担保（未写额度）
- 禁报形态：金额等于本金；未约定复利；担保范围未列违约金
- 默认等级：高
- 建议模板：…

name: missing-clause-audit
description: 审计缺失型与效力型风险——是没写，还是写了但没达到效力标准。
             当规则表述含"未约定/缺失"，或全文按关键词检索不到对应文字时使用。
tags: [contract-review, missing-clause]

# 缺失 / 效力审计

## 三态判定
| 形态 | 判据 | 动作 |
|---|---|---|
| 缺失 | 全文（含表格、附件）按同义词表检索仍无 | 报，锚定最相关条款 |
| 形式具备、效力不足 | 有约定但把效力交给一方单方记录 / 排除法定要件 / 未约定交付存证 | 报 |
| 合规 | 有约定且满足要件 | 不报 |

## 检索词表（按规则族维护）
电子签名：电子签名 / 电子签章 / 数字证书 / CA / 可靠电子签名 / 签署时间戳

## 边界（与系统提示词的"不可判定事项"区分）
- 不可判定：是否真的签了、谁签的、有没有录音录像、是否加粗提示。
- 可判定：条款有没有约定效力标准、有没有约定交付与存证。
- 条款存在 ≠ 合规；"有约定"只完成了三态里的第一种排除。

## 输出
{ "verdict": "missing|insufficient|compliant", "anchor_clause": "第八十三条",
  "evidence": "条款原文片段", "reason": "缺哪一项要件" }
```

### 4.3 `risk-selfcheck/SKILL.md`

```markdown
---
name: risk-selfcheck
description: 输出风险清单前的逐条自检。当已形成 risks 列表、准备输出 JSON 时使用：
             对每条风险核对判据来源、条款归属、引用逐字性与等级依据，任一不通过即删除。
tags: [contract-review, quality-gate]
---

# 输出前自检

对每条风险回答四个问题，任一为"否"→ 删除该条，不要试图修补：

1. 判据来源：判定条件是否**逐字**来自规则卡？是"我认为应该"→ 否。
2. 条款归属：quote 是否在当前 clause_no 的正文里连续出现？
3. 文字支撑：能否指出条款里直接体现该判据的文字？指不出 → 否。
4. 等级依据：risk_level 是否等于规则默认等级，或有卡里写明的升级条件？

## 常见必须删除的情形
- 论证里出现规则卡没有的判据（"金额应高于本金""应区分限额"）
- 拿"与本条无关"的文字去套一条规则（历史误报的主要形态）
- 问题成立但挂错了规则号 → 宁可不报，也不要挂最接近的那条

## 输出
{ "keep": [...], "drop": [{"index": 0, "reason": "criterion_not_in_card"}] }
```

把建议单独发给一个不懂上下文的人，他能否直接替换原文？不能 → 重写。

## 五、怎么接进现有链路

### 5.1 三种接法

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 纯平台 | 把 4 个技能挂到 `contract_review`，提示词加"第 0 步取规则卡、第 6.5 步自检" | 零代码，SSE 可见技能调用，演示友好 | 激活不确定；多 2–3 轮 tool call，耗时上升；一致性可能掉 |
| B 服务端兜底 | `api/server.py` 拿到结果后调 `tools/gate.py`（与技能同源的规则卡） | 确定性 100%，可回归 | 演示时"看不见"，需要日志佐证 |
| **C 双轨（推荐）** | A 负责"过程可见"，B 负责"结果保底"，两者共用同一份 `cards.json` | 既好看又稳 | 需要维护单一事实源 |

### 5.2 单一事实源

```
data/rules/rules.yaml  ──build──▶  data/rules/cards.json
                                        │
                     ┌──────────────────┼───────────────────┐
                     ▼                  ▼                   ▼
        skills/loan-rule-cards/    api 侧 gate         tools/evaluate 分层报告
              cards/*.md            (机械判定)           (按规则族统计)
```

任何规则改动只改 `rules.yaml`，另外三个产物由脚本生成。否则一定会出现"技能里说 A、代码里说 B"的口径漂移。

### 5.3 agent.json 的具体改动

```jsonc
"skill_names": ["loan-rule-cards", "missing-clause-audit", "risk-selfcheck", "suggestion-compiler"],
"verification_config": {
  "enabled": true,            // 当前为 false，兄弟项目（月末结账助手）已启用
  "pass_score": 0.8,
  "strictness": "balanced",
  "fail_policy": "repair_then_controlled_summary",
  "max_final_rounds": 2
}
```

`verification_config` 是平台内置的校验回路，**当前是关闭的**。开启前后必须各跑一次全量 + 3 次一致性，因为它是新的不确定性来源：可能提升自检质量，也可能让输出结构变化。

提示词侧只加两段（不要重写现有闸门）：

```
# 执行步骤（技能）
0. 判任何一条规则前，先调用 loan-rule-cards；取不到规则卡则不得判定。
0.1 规则表述含"缺失/未约定"时，改用 missing-clause-audit 的三态判定。
7. 输出 JSON 前，把 risks 交给 risk-selfcheck，按返回的 drop 清单删除。
   未能完成自检的输出视为无效输出，必须重做。
```

### 5.4 耗时预算

现状单份约 40 秒，上限 2 分钟。技能不是越多越好：

- 规则卡：一次批量取（按合同预分类，4 次调用以内），不要逐条款调用；
- 自检：一轮，全量清单一次过；
- 缺失审计：只对"检索不到"的少数规则触发。

超过 3 轮额外调用就该重新设计——多智能体串行从 40 秒涨到 3 分钟的教训还写在 `DESIGN.md` 里。

## 六、怎么验收，才不是自欺

### 6.1 指标要分层看

现在是 5 个总数。建议同时报：

- **按规则族**：利率 / 担保 / 违约 / 合规四行。R16 一族 4 条误报会被一眼看见。
- **按缺陷类型**：数值超限 / 要素缺失 / 效力不足 / 文本矛盾。这决定技能要不要拆。
- **按合同**：现在 `TEST_REPORT` 有，但 0 标注合同（C01/C02/C11…）的误报率分母是 0，会被算成 100% 或 0%，噪声很大，建议单列。

### 6.2 留出集

28 份合同、75 条计分标注，改动一条就是 1.3pp。**在同一批数据上把 96 调到 100，说明不了泛化。**

建议新增 10–15 份**不同模板**的合同（不同起草方、不同条款顺序、含附件与表格），只用来验证不调参。目标写成"留出集 ≥95% 检出、≤5% 误报"，比"100%"可信得多。

### 6.3 反事实测试（最有说服力的一页）

同一份合同，只改一个要素，看结论是否跟着变：

| 改动 | 期望 |
|---|---|
| R16 条款：`最高债权额为 600 万元` → `以出借人核定的授信余额为准` | 从"不报"变为"报" |
| R38 条款：`可靠电子签名…同等效力` → `以出借人系统记录为准` | 从"不报"变为"报" |
| 罚息：`上浮 50% 且设上限` → `三倍且不受上限约束` | 从"不报"变为"报" |

三组都翻转 → 证明模型在按规则判，而不是按模板背。评委看这个比看 100% 更有感。

### 6.4 成本指标

单份耗时 P50/P95、token 消耗、技能调用次数。技能层如果让耗时翻倍，即使指标涨了 2pp 也不划算。

### 6.5 一致性回归

每次改动跑同一合同 3 次，Jaccard 必须 ≥0.95。技能激活抖动会直接打穿这个指标——这是引入 Skill 最大的回归风险。

## 七、反模式

1. **用 Skill 做定位**。模型输出的字符偏移永远不可靠，100% 定位只能靠"quote 是正文子串 + 代码计算偏移"。技能里最多做"quote 是否逐字"的校验，不做定位。
2. **把合规范式塞进所有场景都会激活的技能**。历史已经证明：反例与被判条款用词雷同，会抬高触发权重。合规定式只能放在"否决式"场景（闸门、规则卡命中即放行），不能放在"参考式"场景。
3. **一个技能管 40 条规则**。正文 500 行以上，加载即污染上下文，等于没做分层。按族拆，用 `<reference>`。
4. **让技能里再跑一遍全量 LLM 审查**。成本翻倍、结论还可能和主流程打架。技能只做"机械校验 + 局部补判"。
5. **用 NL-to-Skill 直接生成核心技能**。它适合脚手架，不适合承载判定口径——规则卡必须逐字来自 `rules.yaml`。
6. **为了指标好看改口径**。比如把"建议可用性"从关键词命中改成"非空即算"，这不叫优化。

## 八、落地路线（按 ROI）

| 步 | 动作 | 工作量 | 预期 | 风险 |
|---|---|---|---|---|
| 1 | 把 `tools/gate.py` 从 2 条规则扩到更多「定式可判」的规则，每条都要有 fp_list 级的复核依据 | 0.5–1 天 | 覆盖更多自造判据 | 过拟合；扩规则必须有复核结论支撑 |
| 2 | 修 R34 数据瑕疵（把「示例市」改成真实地名或明确标注为虚构） | 0.5 天 | 消掉最后 1 条误报 | 低 |
| 3 | 写 `loan-rule-cards`（4 族 `<reference>`），挂到 agent | 1 天 | 减少套错规则；提示词可瘦身 | 激活不确定，需与 B 方案并行 |
| 4 | 写 `missing-clause-audit`，修 R38 规则标题为「效力不足或缺失」 | 0.5 天 | 结构性解决缺失型漏检 | 与"不可判定事项"措辞要同步改，否则继续打架 |
| 5 | 写 `risk-selfcheck` + `suggestion-compiler` | 1 天 | 误报稳定性、建议质量 | 多一轮调用，注意耗时 |
| 6 | 开启 `verification_config`，A/B 对比 | 0.5 天 | 未知，需实测 | 可能改变输出结构、增加延迟 |
| 7 | 扩留出集 + 分层报告 + 反事实三组 | 2–3 天 | 说服力 | 工作量最大，但最值钱 |
| 8 | 技能申请上架租户仓库 | 0.5 天 | 演示"技能仓库/审核"能力 | 需管理员账号 |

**顺序理由**：1–2 步是"确定性的收益"，几乎无风险，先把指标锁死；3–5 步是"能力建设"，让系统在留出集上更稳；6–7 步是"可信度"，决定评委信不信这组数字。

## 九、风险登记

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| 技能激活抖动 | 模型某次没调用规则卡/自检 | 提示词强约束 + 服务端兜底；一致性回归 ≥0.95 才合入 |
| 耗时超 2 分钟 | 逐条款调用技能 | 批量调用、按族取卡、限制技能轮次 ≤3 |
| 平台脚本能力不确定（`run_skill_script`） | 依赖脚本执行 | 先做纯文本技能；机械判定放服务端，平台侧只做"可见" |
| 过拟合测试集 | 在同 28 份合同上调参 | 留出集 + 反事实测试 |
| 口径漂移 | 技能、代码、评测各说一套 | `rules.yaml` 单一事实源 + 生成脚本 |
| 验证回路改变输出 | 开启 `verification_config` | 开关前后各跑全量，保留两份报告 |

## 附：一句话回答"Skill 到底怎么帮我提指标"

> 把"规则怎么判"从常驻提示词搬进按需加载的规则卡（省上下文、少套错），
> 把"判得对不对"从模型自觉搬到可执行的闸门（确定性、可回归），
> 把"演示编排"从口头描述搬到 SSE 里看得见的技能调用（可信度）。
> 三者各司其职，指标才是"被守住"的，而不是"被刷出来"的。
