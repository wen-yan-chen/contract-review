```
data/

├── clauses/     条款切分结果（约 2900 条）

```

**旁白（约 160 字）**

> 数据集全部自造，不含任何真实企业与个人信息。
>
> 二十八份合同，每份 90 到 110 条、一万字上下，四十条规则在每份合同里都有对应条款——

### 板块 4｜Nexent 具体使用过程（1:45）★ 重点

分五小节，**每节都要有截图或录屏**。

#### 4.1 大模型配置（20 秒）

**画面**：模型配置页；再切到一次调用的耗时数字

**旁白**

> 模型只接入一个 deepseek-chat，不做多模型混用——多模型会引入不确定性。
> 温度 0，最大步数 15。实测单份合同调用 25 到 60 秒，平均 35 秒。

#### 4.2 向量知识库（25 秒）

**画面**：知识库页 → 点开文档看分块 → 再回到智能体挂载

**旁白**

> 知识库是检索增强的关键。40 条规则写成一份 34 KB 的 Markdown，
> 上传后被切成 13 个分块。
>
> 向量模型用本地的 bge-m3，1024 维，跑在 Ollama 上，不依赖外部 API。
>
> 有一点是实测得出的：把「合规定式」也塞进知识库，误报反而上升——
> 因为检索按语义相似，反例和问题条款用词雷同，抬高了规则触发权重。
> 所以知识库只放「什么算问题」，「什么不算」放进提示词。

#### 4.3 提示词（30 秒）

**画面**：提示词页面，逐段滚动，停在「判定闸门」和「自证要求」两处

**旁白**

> 提示词 2942 字符，分七段：角色、输出格式、硬性约束、判定闸门、判定边界、
> 不可判定事项、自证要求。
>
> 两段最关键。
>
> 一是判定闸门：明确列出四种合规写法不得报告，并禁止引入规则库未列明的判据。
>
> 二是自证要求：每条风险的第一句必须写出「违反哪条规则的哪项判定条件、
> 条款中的对应文字是什么」；写不出来就删除该条。
>
> 这一段是误报率从 27.7% 降到 6.5% 的直接原因。

#### 4.4 Skills（20 秒）

**画面**：技能仓库列表 → 逐个点开看 SKILL.md 摘要

**旁白**

> 四个自定义技能，各管一个指标。
>
> 规则卡片：按 rule_id 精确返回判定条件、合规定式、缺陷形态和已知误报，压误报。
> 缺失条款审计：做「缺失 / 效力不足 / 合规」三态判定，提检出。
> 输出自检：输出前四问，不通过就删。
> 建议编译：强制建议是可直接替换的完整条款，提建议可用性。

#### 4.5 一次完整调用（10 秒）

**画面**：切到终端，滚动一次 SSE 事件统计

**旁白**

> 一次调用约 1200 个流式事件、3 到 4 个步骤，服务端拼接后取出结构化 JSON。

### 板块 5｜测试过程（1:20）★ 重点

#### 5.1 测试流程（25 秒）

**画面**：终端依次执行三条命令

```powershell
python _scratch\batch_run.py            # 模型原始输出
python tools\gate.py --data-root data   # 过确定性闸门
python tools\evaluate.py --data-root data --out docs\TEST_REPORT.md
```

**旁白**

> 测试分三步：批量跑出模型原始输出、过一遍确定性闸门、再算指标。
>
> 闸门是代码而不是提示词：两条定式——R16 的合规写法否决、R38 的缺陷写法补报。
> 它幂等，第二次跑输出 0 处改动；每处改动写日志，可审计。

#### 5.2 指标结果（30 秒）

**画面**：`evaluate.py` 的表格输出，逐行高亮

```
风险条款检出率      100.0%   ≥85%    达标
误报率                2.6%   ≤15%    达标
原文定位准确率      100.0%  =100%    达标
风险等级一致率      100.0%   ≥85%    达标
修改建议可用性       96.0%   ≥85%    达标
三次一致性(Jaccard)  1.000  ≥0.90    达标
```

**旁白**

> 二十八份合同、七十五条计分标注上的结果：检出百分之百，
> 误报百分之二点六，定位和等级都是百分之百，建议可用性百分之九十六。
>
> 同一份合同连跑三次，风险集合完全一致。

#### 5.3 优化过程（25 秒）

**画面**：PPT 阶梯图（38% → 27.7% → 6.5% → 2.6%）

**旁白**

> 误报率不是一开始就低。
>
> 第一阶段 38%；复核 28 条误报后发现，25 条不是编造，而是**规则套用错误**——
> 把「意向书失效」归到「解除后清算」，把「只有诉讼管辖」归到「诉讼与仲裁并存」。
>
> 第二阶段修数据，27.7%；第三阶段加自证要求，6.5%；最后加确定性闸门，2.6%。

### 板块 6｜前端演示（1:20）★ 重点

**画面**：浏览器实操，全程不剪断操作连贯性

| 时间 | 操作 | 必须入镜 |
|---|---|---|
| 0:00–0:25 | 拖入 C03 合同 | 状态条三行：解析中 → 已解析 106 条 → 审查完成 6 处 |
| 0:25–0:50 | 点「高」筛选，点第一条卡片 | 左栏自动滚动 + 高亮 |
| 0:50–1:05 | 讲单条风险四字段 | 原文 / 问题 / 建议 / 依据 |
| 1:05–1:20 | 授信比对 + 导出 Word | 三项差异 + 文件打开 |

**旁白（约 260 字）**

> 把合同拖进来。系统先解析文件、按「第X条」切分，同时对每条建立字符级索引。
>
> 这一步要强调：切分和偏移是代码算的，不是模型给的。定位要精确到字符，交给模型就不可控。
>
> 四十秒后，六处提示。按等级筛一下，两条高风险。
>
> 点开第一条：左栏自动定位到原文并高亮。四件事说清楚了——
> 原文是哪一句、为什么是问题、应该改成什么、依据有没有。
>
> 建议不是「建议完善」，而是可以直接替换的条款表述。
> 依据如果没检索到权威条文，它会写「未检索到权威依据」，而不是编一个法条。
>
> 如果同时给了授信批复，会比对要素：这里利率比批复高 15BP、担保方式不一致、
> 批复要求的自有资金比例没写进合同，三项都会提示。
>
> 结果可以导出 Word，带免责声明，可直接归档。

### 板块 7｜架构总结（0:35）

**画面**：PPT 架构图 + 请求链路六个环节

**旁白（约 130 字）**

> 架构三层：前端负责展示与联动，服务层负责解析、切分、闸门和导出，智能体负责判断。
>
> 一次审查六个环节：上传、解析、切分、调智能体、过闸门、落盘展示。
>
> 职责边界很清楚：位置由代码算，判断由模型做，依据必须可溯源。
> 这也是定位能做到百分之百的原因。

### 板块 8｜项目收获（0:25）

**画面**：PPT 收尾页（三条收获 + 仓库地址）

**旁白（约 90 字）**

> 三点收获。
>
> 一，模型的错误大多不是「编造」，而是「套错规则」——修复方向应该是让它自证，不是加大模型。
> 二，数据集的质量决定指标的上限：合同里没有的条款，模型报出来就是误报。
> 三，把不确定性留在代码边界之内，比反复调提示词更可靠。
>
> 代码、数据、文档都在仓库里，一条命令可以复现。
