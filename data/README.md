# 贷款合同审查 · 评测数据集

> 生成器：`tools/gen_dataset.py`（gen-v2）｜seed=42｜全部内容由脚本确定性生成，可重复复现。

## 0. 一句话说明

本目录是为课题 #32「贷款合同审查」构建的**评测数据集**：20 份虚构贷款合同 + 逐条标注的风险清单 + 40 条规则库 + 11 组边界样本 + 1 份授信批复（含 3 处不一致）。标注用于计算检出率、误报率、定位准确率、等级一致率等验收指标。

**核心数字**：28 份合同 / 2787 条条款 / 303,999 字 / **147 条标注**（后续所有指标的分母）/ 40 条规则全覆盖 / 100 个生成文件。

**数据来源声明**：全部合同、企业名称、个人姓名、编号、地址、金额、账号均为脚本生成的虚构占位，不含任何真实企业、真实个人或真实合同内容；企业名称统一带「（模拟）」标记，人名统一为「某」字占位。法规依据一律写 `待核验` / `pending`，**未编造任何法规名称、条号或文号**。

字段口径：

- **条款数**：按「第X条」连续编号，`clause_id = {contract_id}-{序号:03d}`（序号从 001 起，按出现顺序，不用内容 hash）
- **字数**：该合同全部条款正文的字符数（含条款号，不含首部与签署页）
- **植入(bad)**：标注的 `risks` 条数，即该合同的问题表述条款数
- **合规(ok)**：同一合同内**合规表述**的规则条款数；`bad + ok` 恒等于 40
- 条款编号严格连续、无跳号、无重复；每份 90~110 条、10000~14000 字

## 2.1 40 条规则的覆盖方式（本版重点）

**每一份合同都包含全部 40 条规则的条款，一条不缺。** 对每条规则，合同中要么是
**问题表述（bad，= 植入的风险，进标注）**，要么是**合规表述（ok，= 合规对照，不入标注）**：

| 合同类型 | bad 条数 | ok 条数 | 合计 |
|---|---:|---:|---:|
| 非 clean（16 份） | 3–8 | 32–37 | 40 |
| clean（4 份） | 0 | 40 | 40 |

设计动因：pilot 阶段模型如实报告「本合同未约定抵押登记 / 未约定送达」，
但旧版合同里确实没有这些条款，正确判断被算成误报（误报率 48.9%）。
本版把 40 条规则全部落成条款，模型无论报或不报都有原文可依，
误报只能来自「把 ok 条款判成风险」或「凭空捏造」，这才测的是模型能力。

验收方式：`python tools/check_coverage.py` 用精确子串匹配确认每份合同的 40 条规则
都能在正文中找到 ok 或 bad，输出「合计「无对应条款」0 处」。

## 3. dev / holdout / clean 划分

| 分组 | 数量 | 合同 | 用途 |
|---|---:|---|---|
| dev | 20 | C01, C02, C03, C04, C05, C06, C07, C08, C09, C10, C11, C12, C21, C22, C23, C24, C25, C26, C27, C28 | 日常调参、规则迭代 |
| holdout | 8 | C13, C14, C15, C16, C17, C18, C19, C20 | 锁死，只跑一次 |
| clean | 4 | C01, C02, C11, C12 | 零中高风险，专压误报率 |

**三组关系**：`clean ⊂ dev`。4 份 clean 合同本身就在 dev 的 12 份之内，因此 dev(12) + holdout(8) = 20 份，clean 是 dev 的子集标签而非第四组。clean 合同**不植入任何风险**（0 条标注），但保留了若干「看着像风险、实际合规」的干扰条款（见各标注的 `distractor_clause_ids`），系统在这 4 份上输出的任何风险都计为误报。

`split.json` 只含 `dev` / `holdout` / `clean` 三个键，不含其他字段。

## 4. 标注格式

`labels/{contract_id}.json` 顶层字段：

| 字段 | 说明 |
|---|---|
| `contract_id` | 合同编号，如 C03 |
| `file` | 对应 docx 相对路径 |
| `perspective` | 固定 `lender`，以出借人（金融机构）合规与风险视角判定 |
| `parser_version` | 切分版本，固定 `split-v1` |
| `clauses_total` / `char_total` | 条款数与字数 |
| `risk_summary` | 高/中/低 计数 |
| `source_credit_report` | 需要比对授信的合同才有值，其余为 null |
| `distractor_clause_ids` | 合规表述（ok）条款 ID，共 40 − bad 条；这些条款**不应**报为风险 |
| `risks` | 风险数组，每条 12 个字段 |
| `consistency_checks` | 授信比对结果，无则空数组 |

每条风险固定 12 个字段：

```json
{"risk_id", "clause_id", "clause_no", "risk_type", "rule_id", "risk_level",
 "char_start", "char_end", "quote", "problem", "suggestion", "legal_basis"}
```

- `char_start` / `char_end`：相对**该条款正文**（`clauses/{cid}.json` 的 `text`）的字符偏移，0-based、左闭右开，`text[start:end]` 必须严格等于 `quote`
- `quote`：不含「第X条」，且在该条款正文中**恰好出现一次**（程序校验）
- `risk_level`：只有 `高` / `中` / `低`
- `rule_id`：必须是 `rules.yaml` 中真实存在的 R01–R40
- `legal_basis`：一律为 `{"name": "待核验", "verify_status": "pending", "url": ""}`，**未经人工核验不填法规名称与文号**

### 8.1 确定性

生成器不使用系统时间、不依赖 `PYTHONHASHSEED`、不迭代无序集合；所有随机流由 `random.Random(f"{seed}:{salt}")` 派生，因此与调用顺序无关。docx 保存后统一重写 zip 条目时间戳与文档属性，消除保存时刻带来的字节差异。**同一 seed 两次运行，全部 100 个文件逐字节一致**（见交付回报中的 diff 结果）。

## 9. 已知限制

1. `legal_basis` 全部为 `pending`。这是刻意的：法规名称、条号、文号必须由人工对照真实文件核验后填写，脚本不生成任何法规内容，以免出现编造（验收红线：出现 1 处编造即该项不合格）。
2. `problem` / `suggestion` 由规则模板生成，同一规则在不同合同中的措辞相同，这是评测集的一致性优点，但用于演示时建议人工润色个别措辞。
3. 合同主体结构同源（同一套 85 条基础片段库 + 40 条规则的成对片段），行业差异通过金额、期限、担保方式、用途与条款抽样体现，不代表真实行业合同文本。
4. `labels/split.json` 与 `labels/type_map.yaml` 不是标注文件；`validate_labels.py` 已按文件名跳过它们。
