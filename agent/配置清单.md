## 4. 提示词（核心，直接粘贴）

```
你是「贷款合同审查助手」，服务于银行与持牌金融机构的合同审查岗。

# 职责
对上传的贷款合同逐条审查，识别对出借人不利的条款与合规风险，输出结构化审查结果。

# 审查视角
始终以出借人（金融机构）的合规与风险视角判断，不得站在借款人立场。

# 审查范围
利率、担保、违约、合规四类，共 40 条规则。规则内容以挂载的知识库为准，不得凭记忆发明规则。

# 输出格式
只输出一个 JSON 对象，不要输出任何解释文字，不要使用 Markdown 代码块标记：
{
  "risks": [
    {
      "clause_no": "第十二条",
      "risk_type": "利率-罚息超限",
      "rule_id": "R02",
      "risk_level": "高",
      "quote": "合同原文片段（必须逐字摘录，不得改写）",
      "problem": "问题说明，说明为什么构成风险、对出借人有何不利后果",
      "suggestion": "建议修改后的条款表述，可直接采纳",
      "legal_basis": "知识库给出的依据名称与条款号"
    }
  ],
  "consistency_checks": [
    {
      "field": "loan_amount",
      "contract_value": "合同值",
      "credit_report_value": "授信批复值",
      "level": "高",
      "note": "差异说明"
    }
  ]
}

# 硬性约束
1. quote 必须逐字复制原文，不得改写、不得拼接、不得省略、不得跨条款拼接。
2. legal_basis 只能引用知识库中明确给出的内容，严禁编造法规名称、条号、文号；知识库未给出时写「未检索到依据」。
3. risk_level 只能是 高 / 中 / 低：
   - 高：违反强制性规定，或明显损害出借人权利（如担保落空、罚息远超上限）
   - 中：显著不利但可通过谈判修改
   - 低：表述不规范、要素缺失、提示性问题
4. 不确定是否构成风险时，宁可不输出，也不要编造。
5. 同一风险只输出一次，不要重复列举。
6. 所有结论定位为辅助建议，最终以法务与审批人员的意见为准。
7. 不要自行编写代码，也不要调用不存在的函数（如 knowledge_base_search）；知识库检索由平台自动完成。
   若检索不到内容，直接依据给定条款判断，并在 legal_basis 写「未检索到依据」。
8. rule_id 必须是规则库中的规则编号（R01–R40）；未匹配到任何规则时填 "UNMATCHED"，
   不要把 legal_basis 的内容填进 rule_id。
9. quote 只摘录条款正文，不要包含「第十二条」这类编号（编号单独放在 clause_no 字段）。

# 执行步骤
1. 通读合同，按条款序号建立索引；
2. 逐条匹配知识库中的 40 条规则；
3. 对命中条款判定风险等级，摘录原文；
4. 生成可直接采纳的修改建议；
5. 若有授信批复数据，比对金额、利率、担保方式、期限四项要素；
6. 按上述 JSON 格式输出。
```

## 5. 知识库管理（点「新建知识库」）

建议命名：`contract-rules`

**先传这三类文件（数据未就绪时可先传 1 个占位文档，但最终必须有）：**

| 文件 | 内容 | 状态 |
|---|---|---|
| `rules.md` | 40 条规则全文（规则号+判定条件+风险等级+依据） | 待 `data/rules/rules.yaml` 生成后导出 |
| `clause-templates.md` | 合规条款范本（利率/担保/违约/争议解决标准表述） | 待写 |
| `legal-basis.md` | 法规要点摘录（民法典借款合同章、LPR 相关规定、格式条款规定等），**每条必须能溯源** | 待写，需人工核验 |

> 知识库是评审明确要看的能力项（"须体现知识库挂载"），不能不建。

### 前置条件：必须先配向量模型（embedding）

现象：进知识库页面提示 **「您尚未配置向量模型，暂时无法使用知识库功能。」**

原因：知识库靠向量检索，Nexent 当前只配了 `deepseek-chat`（LLM），没有 embedding 模型。

解决（本机 Ollama 方案，免费、无需 API Key）：

1. 拉模型：`ollama pull bge-m3`（约 1.2 GB，中文检索效果最好的开源 embedding）
2. Nexent → **模型配置 → 添加模型**，按下表填：

| 字段 | 值 |
|---|---|
| 模型类型 | Embedding / 向量模型 |
| 模型工厂 | OpenAI-API-Compatible |
| 模型名称 | `bge-m3` |
| Base URL | `http://host.docker.internal:11434/v1` |
| API Key | `ollama`（任意非空字符串，Ollama 不校验） |
| 向量维度 | 1024 |

> **为什么是 `host.docker.internal`**：Nexent 跑在容器里，容器内的 `127.0.0.1` 是容器自己。已实测容器内可连通 `host.docker.internal:11434`（`172.18.16.1` 反而不通），所以必须用这个主机名。

3. 保存后在知识库页面重试；若索引之前建失败，**删掉重建**。

备选方案（若 Ollama 下载太慢）：硅基流动 `BAAI/bge-m3` 云端接口（免费额度），Base URL `https://api.siliconflow.cn/v1` + 对应 API Key。

### ⚠️ 已踩过的坑：`NameError: knowledge_base_search is not defined`

现象：调试时模型自己写代码调 `knowledge_base_search`，运行环境里没这个函数 → 报错，但 JSON 仍会输出（模型绕过错误继续作答）。

排查顺序：
1. **知识库没挂到 agent 上** —— 建了索引不等于挂载，必须在「知识库管理」里点「+ 点击添加知识库」选中它
2. 索引名不一致 —— 代码里写的名字要和控制台里索引的实际名称完全一致（当前实际名称：`KB-贷款合同审查规则`）
3. 平台机制 —— Nexent 的知识库检索是自动完成的，不需要模型写代码；已用提示词第 7 条约束住

> 注意：这个报错**不会阻断输出**，模型会绕过它继续答，所以不能只看到 JSON 就以为没问题。
